# HR Web App Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the HR area frontend (`apps/hr-web`), a Next.js 16 App Router app that lets one HR user sign in, browse candidates per role, see suggested scores and reasoning, override scores with a reason, watch and retry scoring jobs, import the data pack, and create candidates.

**Architecture:** A BFF proxy. The browser never holds a JWT; both tokens live in httpOnly cookies set by `apps/hr-web`. All FastAPI access happens server-side in route handlers that read the access cookie, attach it as a Bearer token, and transparently rotate on `401` (single-flight) before retrying once. Pages are client components that fetch same-origin `/api/*` route handlers.

**Tech Stack:** Next.js 16 (App Router), TypeScript, Tailwind CSS v4, zod, Vitest + React Testing Library, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-18-hr-web-design.md` (accepted).

## Global Constraints

- Next.js 16 App Router, TypeScript, Tailwind CSS v4; Node.js 20.9+.
- Cookie names are exactly `hr_access` and `hr_refresh`; both HttpOnly, Secure in production, SameSite=Lax, Path=/.
- Tokens never appear in browser JS, localStorage, sessionStorage, or `NEXT_PUBLIC_*` variables.
- The FastAPI base URL is the server-only env var `API_ORIGIN` (e.g. `http://localhost:8000`).
- Scoring statuses are exactly `queued` | `scored` | `failed` | `needs_a_person`.
- A `failed` scoring job is never rendered as a score.
- Error responses from the API are RFC 7807 problem details; surface `detail` to the user.
- Validation uses zod; the override score is an integer 1..4 and `override_reason` is non-empty.
- No heavy UI library; use hand-rolled primitives only.
- All file paths below are relative to the repo root and live under `apps/hr-web/`.

## Review Focus

1. **A `failed` job renders "failed", never a number.** Condition: `ScoringStatus === 'failed'`. Expected: badge shows "failed" text and no score. -> Task 8 (`ScoringBadge` test).
2. **An expired access token refreshes transparently.** Condition: FastAPI returns `401` while a valid refresh cookie exists. Expected: the original call is retried once with the new token and succeeds. -> Task 3.
3. **Concurrent `401`s rotate the refresh token exactly once.** Condition: two requests receive `401` at the same time. Expected: one refresh call, both retries succeed (single-use token not burned twice). -> Task 3.
4. **An override with empty reason or out-of-range score is rejected before the API.** Condition: whitespace-only `override_reason` or `final_score` outside 1..4. Expected: schema rejects and the form shows an inline error. -> Task 2 and Task 12.
5. **An unauthenticated visitor is redirected to `/sign-in`, not shown a broken page.** Condition: protected route with no `hr_access` cookie. Expected: proxy redirects to `/sign-in`. -> Task 5.
